# [FIXED] 0.31.1 busy 语义漂移 — execute_prompt 假超时 + poll.py 永不判定完成

> 状态: FIXED（v2.21，2026-08-03 真实 0.31.1 实测闭环） | 版本: kimi-code 0.29.0 → 0.31.1（changelog 未声明）
> 现象入口: `execute_prompt` 报 `MCP error -32001: Request timed out`，但 60s 后 prompt 实际已注入；`poll.py` 后台监控永不判定完成

---

## 一、表现

| 症状 | 细节 |
|------|------|
| `execute_prompt` 假超时 | 目标 session 主 turn 空闲（用户视角"没在干活"）仍 30s MCP 超时（-32001）；超时后 60s prompt 实际注入成功，但用户拿不到 `poll_command` |
| `poll.py` 永不完成 | 状态轮询判定 session 一直 busy → 300s 后 `[POLL_TIMEOUT] exit 3`，fetch 到的回复错位 |
| 状态缓存污染 | `poll_session`/`waitForStatus` 的 WS 缓存长期为 `running` |

## 二、根因（两层，均在 0.29.0 → 0.31.1 之间产生，官方 changelog 无任何声明）

### 1. `busy` 字段语义扩大（主因）

0.31.1 实测（WS 事件流实锤，turn 结束但后台任务 running）：

```
event.session.work_changed { busy: true, main_turn_active: false, pending_interaction: "none", last_turn_reason: "completed" }
```

- **0.24-0.30**：`busy == false` 即空闲（v2.17 实测依据）
- **0.31.1**：`busy` 含**后台任务/持续活动**——只要 session 有 running 后台任务，turn 结束后 `busy` 仍为 `true`；后台任务结束才归 `false`。真正的主 turn 信号是 **`main_turn_active`**（字段 0.27 起就存在，v2.20 未启用）

旧判定 `busy==true → running` 把空闲 session 误判忙碌：
- `submitPrompt` 前置 `waitForStatus(60s)` → 吃满 60s → MCP 30s 协议超时先触发 → 客户端显示 -32001；60s 后 tunnel 仍静默提交（客户端已断开，造成"报错但实际已注入"）
- `poll.py` 状态永不 `idle` → 超时退出

### 2. `handleDirectEvent` 漏传 `main_turn_active`（修复时发现）

`work_changed` 事件归一化调用只传了 `{busy, pending_interaction}`，**未传 `payload.main_turn_active`** → 事件 `busy:true + mta:false` 仍被映射为 `running` 写入状态缓存 → `getSessionStatus` fast path（30s TTL）命中陈旧 running → `waitForStatus` 等满 25s 报 busy。REST 路径（`getSessionStatus` 补取详情）判定正确，WS 路径与 REST 路径不一致。

## 三、修复（v2.21，3 处 + 等待策略）

| 文件 | 变更 |
|------|------|
| `src/status-normalize.ts` | 判定优先级：`status` 枚举 > `pending_interaction` > **`main_turn_active`** > `busy`；`SessionDetailBody` 增 `main_turn_active` |
| `src/wire-client.ts` | ① `handleDirectEvent` work_changed 补传 `payload.main_turn_active`；② `submitPrompt` 前置等待 60s → **25s**（< MCP 30s 协议超时），非 idle 明确抛 `Session is busy (status: ...)`，移除 autoApprove 58s 二次重试；③ `sendPrompt` Step 0 同步 25s |
| `src/poll-command.ts` | POLL_SCRIPT：`busy=true` 时补查详情 `pending_interaction` → `main_turn_active`，主 turn 空闲即 `idle`；`fetch_result` 失败/无文本写 `[POLL_FETCH_FAILED] {原因} @ {时间}` 覆盖旧文件（防误读残留） |

## 四、验证（真实 0.31.1 环境，全矩阵）

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 后台任务 running + 主 turn 空闲，`execute_prompt` | 25-60s 等待 → 假超时/误报 busy | **秒级 `submitted: true`** |
| 短真忙 turn，`execute_prompt` | 吃满 60s → MCP 超时 | 事件驱动等待 → turn 结束自动提交（秒级） |
| 长真忙 turn（>25s），`execute_prompt` | MCP -32001 | **25s 内明确报 `Session is busy`** |
| `poll.py` 监控后台任务 session | `[POLL_TIMEOUT] exit 3` | 立即判定 idle → `exit 0` + 正常 fetch |
| `poll.py` 无回复/fetch 失败 | 旧文件残留（误读风险） | `[POLL_FETCH_FAILED]` 覆盖 |

- 单测：`tests/status-normalize.test.mjs` +5 例（busy+mta 组合、pi 优先、mta 缺失回退），43/43 全绿
- WS 事件：0.31.1 `work_changed` **推送正常**（60s 探测捕获完整事件流，载荷含 `main_turn_active`）；此前"事件断链"判断为首轮探测窗口内恰好无状态变化的误报
